3. ESTADO DO CONTRATO RC.1

O RC.1 já descrevia a arquitectura alvo com boa precisão, mas usava uma main backend anterior,
deixava D-01..D-08 sem decisão formal e não possuía manifesto/OpenAPI versionados. A auditoria
actualizou a evidência para a main exacta, classificou decisões e congelou o alvo como RC.2 porque
D-05 merchant→unidade continua blocking e sem mapping persistido na main.

4. RELAÇÃO COM PONTO MVP V1

Foram auditados CONTRATO_CONSUMA_PONTO_MVP_V1.md, CONSUMA_PONTO_MVP_V1.contract.json e
CONSUMA_PONTO_MVP_V1.openapi.json integrados na main. PONTO é o contrato operacional do
estabelecimento; Android V1 é a facade pública do consumidor. A invariante compartilhada é:
pedido não aceite não possui ordem de pagamento. Criação Android projecta
PENDING_ACCEPTANCE / NOT_PAYABLE / paymentAvailable=false. Somente aceite válido projecta
ACCEPTED / UNPAID e pode tornar paymentAvailable=true por policy.

9. IDs

UUID v4 lowercase imutável para merchant/catalog/category/product/optionGroup/option/quote/order.
PK Long permanece interna; slug é somente alias de apresentação. public_id + uniques/backfill e
constraints tenant-aware são REQUIRED_BEFORE_ENDPOINT.

10. MONEY

JSON exclusivo {amountMinor: integer int64, currencyCode: "AOA"}. Expoente AOA: 2.
Android: Long. Backend: setScale(2, UNNECESSARY), movePointRight(2), longValueExact.
BigDecimal/double/float/decimal textual não aparecem no contrato público.

11. PAGINATION

HTTP zero-based: page default 0; pageSize default 20, máximo 100; desempate UUID público ASC.
Adapter Android converte domain page N para HTTP max(1,N)-1.

12. CATALOG

catalogVersion e productVersion são inteiros positivos monotónicos serializados como strings.
Produto, categoria, preço, opções, disponibilidade, publicação, promoção, moeda e fulfillment/taxa
comercial incrementam catalogVersion na mesma transacção. Main não oferece esta garantia hoje.

13. OPTIONS

VariacaoProduto é estruturalmente incompatível. Decisão: NEW_MODEL_REQUIRED com grupos/opções,
min/max, required, singleChoice, defaultSelected, sortOrder, additionalPrice e available.
Backfill legado somente explícito, validado e no caso simples aprovado.

14. QUOTE

POST /checkout/quotes é autoridade obrigatória: resolve merchant/tenant/publicação/catálogo/
produto/opções/disponibilidade/fulfillment/endereço, recalcula preço, gera snapshot, totals,
expiresAt e divergences. Não cria Pedido, OrdemPagamento nem gateway transaction.
TTL congelado: 10 minutos, configurável por ambiente/policy.

15. FULFILLMENT

Checkout V1 aceita PICKUP e DELIVERY. Mapping merchant→instituição/unidade/rota/cozinha deve ser
explícito e persistido; primeira unidade encontrada é proibida. Ausência: MERCHANT_UNAVAILABLE.
Esta lacuna é BLOCKER_BEFORE_QUOTE_OR_ORDER. Turno é resolvido/locked antes de qualquer Pedido;
quando obrigatório e ausente, rollback total e quote não consumida.

16. ORDERS

POST /orders aceita apenas quoteId, quoteVersion, customer e clientReference. Não aceita items,
nomes comerciais, preços, subtotal, taxas, total, payment amount ou IDs internos. Consome snapshot
autoritativo e cria origem CONSUMA_AQUI_ANDROID; enum/migration ainda são necessários.

17. IDEMPOTENCY

Scope: client instance + endpoint + key. Mesma key/hash faz replay; key igual/hash diferente dá
409 IDEMPOTENCY_CONFLICT; lease em processamento dá REQUEST_IN_PROGRESS. Exactly-one order.
Retenção default configurável: 72 horas.

18. TOKEN

Estratégia escolhida: HMAC versionado de domínio+orderPublicId+salt aleatório, saída opaca >=256
bits, guardando salt, key version e hash de verificação, nunca plaintext. Replay por 72 h reconstrói
o mesmo token; rotação mantém key version antiga pela janela; hash valida consulta; revogação é
persistida. Breach apenas da DB não revela o segredo. Token errado/expirado/revogado e order
inexistente/cross-tenant recebem 404 uniforme. TTL default: 90 dias após terminal, configurável.

19. STATES

Operacionais públicos: PENDING_ACCEPTANCE, ACCEPTED, PREPARING, READY, COMPLETED, REJECTED,
CANCELLED. Financeiros: NOT_PAYABLE, UNPAID, PAYMENT_PENDING, PAID, REFUNDED.
Enums internos nunca são serializados directamente.

20. PAYMENT INVARIANT

Main verifica StatusPedido.EM_ANDAMENTO antes de OrdemPagamentoService criar ordem e o aceite
preserva estado financeiro antes dessa chamada. Android não cria/inicia/exibe pagamento. NAO_PAGO
pré-aceite projecta NOT_PAYABLE. paymentAvailable exige aceite, pedido não terminal, método
permitido e infraestrutura activa.

21. ERRORS

Facade Android garante {error:{code,message,retryable,fieldErrors,traceId}}. ErrorResponse interno
não precisa ser substituído globalmente; adapter público traduz e não expõe stack/SQL/classes/PK.
TURNO_ABERTO_OBRIGATORIO interno mapeia para MERCHANT_UNAVAILABLE sem detalhe excessivo.

22. TENANT ISOLATION

Tenant é resolvido no servidor por merchant→quote→order. Android não envia tenantId,
businessAccountId, institutionId ou unitId. Override é INVALID_REQUEST/campo desconhecido.
Cross-tenant é indistinguível de inexistente.

23. SECURITY

HTTPS obrigatório; POST <=64 KiB; PII mínima; tokens nunca logados; idem key mascarada; UUID
anti-enumeração; rate limit; imagens HTTPS/allowlist; no-store sensível; sem IDs internos/stack.

24. PII

delivery province, municipality, area, street/reference, building/house, reference point, recipient
name/phone e instructions. Decisão: PII_SAVEDSTATE_REMOVAL_REQUIRED na fase
ANDROID-REMOTE-CONTRACT-INTEGRATION-001, antes de dados reais. Nenhuma source foi alterada aqui.
